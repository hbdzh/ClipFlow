# ADR-0007：先完成macOS首版，再依次推进鸿蒙与Windows

- 日期：2026-11-09；状态：Accepted（用户直接指定排期，Integration审定文档一致性）。
- 来源：用户要求“改一下任务卡，先把macos端做完，再做鸿蒙和windows端”。
- 范围：任务顺序、完成门禁、职责和依赖关系；不改变接口、SDK最低版本、依赖、许可证策略或实际平台能力。

## 决定

采用 **macOS首版完成 → 鸿蒙PC首版完成 → Windows首版完成**。替代ADR-0001/初始技术方案/INT-001计划中的鸿蒙优先与三端Spike并行排期；历史结论保留，不重写旧实测。G0–G5保留能力分类，平台证据分别验收，不再以完整三端G1或INT-002阻塞macOS转码/AI开发。

“macOS做完”按技术方案§1.1的首版能力定义，不止UI-001单段流复制：工作区与系统交互、快速/精确剪辑、常用转码和批处理、至少一个许可明确且实测的人声/伴奏模型、安全输出、开发包和独立QA。PROD-002先冻结具体支持矩阵与失败用例，当前arm64证据不等于Intel支持；必选项未实现、mock或BLOCKED不得算完成。正式签名/公证/商店发布仍须单独授权，多轨NLE/复杂特效/任意模型与全格式不自动进入本次范围。

INT-MAC-001通过才恢复鸿蒙新增实现；INT-HOS-001通过才启动Windows；INT-WIN-001之后由INT-002汇总三端，不能把平台能力差异隐藏为一致支持。平台阻塞不触发自动跳过，重排需要后续用户指令。

## 当前事实与保留现场


当前main的历史文档可能只反映各次交付时状态；本次更新README和任务卡的UI合并状态，不把未合入的鸿蒙报告当成主线已有文件。未来整合鸿蒙分支时需合并本次新排期，禁止用旧任务卡覆盖。设备/SDK缺口据实记录，暂停新增实现是排期调整，不是技术问题已解决。

## 责任与接口边界

| 行为 | 唯一责任 |
|---|---|
| 功能范围、依赖、平台门禁、ADR与契约审批 | Integration；契约与Core联合审定 |
| 共享业务、任务/取消、媒体参数、平台媒体adapter | Rust Core；保持跨端统一语义 |
| 原生UI、授权/文件系统、播放/系统交互、薄桥接 | 当前阶段平台实现；不自行制定FFmpeg业务 |
| 黄金预期、媒体物理结果、真实GUI/开发包与独立接收 | QA；实现方自测不能替代 |

本次公共类型/八个FFI函数/JSON schema均不变，无迁移。后续精确重编码、转码/队列及AI扩展先由Integration/Core审定契约与兼容策略、成功和失败案例；依赖/模型/最低版本变化另作许可与ADR审查，不由本排期文档预批准具体实现。

## 风险、验收与回滚

- 后移鸿蒙会延后暴露商用PC/ABI、URI/权限、helper和模型兼容风险；保留已有阻塞，隔离平台adapter，不能为适配改变共享业务语义或误报能力。
- macOS首版范围大于已有闭环；PROD-002应逐项固定实现卡与可验证条件，不能用“基础UI完成”冒充产品完成，也不无限扩展为所有参考软件功能。
- 成功接收示例：冻结范围必选功能真实执行并由QA接收，INT-MAC-001形成报告后进入鸿蒙。
- 失败示例1：模型只有mock/未经许可或输出时长不合格，macOS首版不接收，不能直接转入鸿蒙。
- 失败示例2：开发包需要未记录的本机工具路径/源文件被覆盖/取消残留，保留错误并修复，不能用宿主单测代替端到端结果。
- 本次文档验收只检查任务依赖、排期一致、链接、结构和diff；不宣称执行了新功能/新平台测试。回滚/再次重排须记录新的用户决定，保留当前历史与未提交工作，不自动恢复旧并行排期。

## 责任边界

| 层 | 唯一职责 |
|---|---|
| 原生平台 | 文件授权与用户交互；不自造模型/任务/音频策略 |
| Rust media-domain | 严格验证配置、请求、固定模型与媒体范围 |
| Rust orchestrator | 单一队列、ID/状态、重任务 permit、取消/超时、关闭与资源所有权 |
| Rust backend | 验源/目标与身份、独立 worker/后代生命周期、配额、输出校验和目录事务、失败隔离 |
| 受控 worker | 固定模型 CPU 推理、受限阶段文件和两个 WAV；不可自行发布目标或后台下载 |
| Integration / QA | ABI/契约/许可证及强制复审；独立媒体/失败/平台验收 |

## 决策理由

采用同父目录的私有 staging 和 macOS 排他目录重命名发布两 stem，避免两个文件独立发布产生半组；不支持独占原语的目标应安全失败，不能退化为覆盖式 rename。单次 rename 的可见性、目标无覆盖不等于断电持久性或解决同 UID 暂存替换；实际授权、目录身份、恢复与隔离边界仍须验证。取消必须先回收所有实际子进程和 staging，再转换已确认的终态；取消与提交由同一状态机确定先后。未知清理状态隔离并保留 ownership。

UMX 采用固定图/权重哈希和流式分块：全局 STFT、3层双向 LSTM 按方向传递完整 hidden/cell，盘上保存有界中间特征，增量 iSTFT；历史有限上下文拼块未达到整段参考阈值，不接纳为等效方案。现有实验只证明特定设备/素材/代码路径，非将 ORT、Python 或数据集的许可/资源/质量自动推广到产品。首个开发范围是 44.1k stereo float WAV 2049..26460000 帧；最终仍须覆盖 AC19 的 44.1/48k、mono/stereo、WAV/FLAC/MP3/M4A、10分钟等，不得降低门槛。

## 风险、测试和回滚

先写 ABI/旧配置、错误与成功契约测试，再实现；强制复审路径身份、无覆盖、unsafe/系统调用、FFI、线程、worker加载、进程树及错误清理。独立 QA 检查真实源/输出哈希、两 stem 的实际解码/对照、取消/崩溃/超时/PID/暂存、冲突、磁盘和权限失败；AC21 独立参考、盲听和跨块边界不得用模拟代替。未明确完整发行构建和 NOTICE/SBOM/LGPL 义务时仍为发行 NO_GO，不将实验依赖/模型权重直接入库。路径可用性与许可证应由实际审核，其他平台与沙盒未验证。

回滚：缺失 `ai_backend` 或无法通过固定身份/资源/平台检查时 ai_separation unavailable；不启动worker、不访问模型，不自动下载，也不变更旧 mock/剪辑/转码行为。后续事务、安全、实现与独立验收均需再审；本文件不是完成证据。

2026-11-10 Integration/Core 确认：禁用 AI 时对 schema 有效且 operation=ai_separate 的对象优先返回 `MS_E_UNSUPPORTED_OPERATION`，即使其他 AI 字段不完整；启用后才校验 AI 专属字段。预检业务拒绝响应 operation 固定 `ai_separate`。当前仅实现严格解析与部分只读路径拒绝，有效请求仍 unsupported、capability=false；这是开发接口结论，不等于产品功能接收。

开发时锁定/实测直接依赖：Python 3.13.3、NumPy 2.2.6、ONNX 1.18.0、ONNX Runtime 1.22.1、SoundFile 0.13.1；模型及依赖版本/来源与 wheel 哈希见 开发清单。这并不证明已安全固定全部解释器、framework、动态库、传递依赖或发布 SBOM；实际发行构建必须再次审查其 NOTICE、LGPL 源码和可替换等义务，发行仍 NO_GO。

2026-11-10 补充开发决策：Core/Integration 同意 `ai_backend.development_root` 可选开关及 [AI-001 受控队列开发限定](../../contracts/AI-001.md#受控队列开发路径2026-11-10-integrationcore-修订非产品接收)。缺省保持旧拒绝；显式 root 仅用于拥有者相同、0700、路径/文件受限的本机可信测试，实际 job 必须接入现有队列、heavy permit 和统一资源 owner，并由 `python -I` 与环境白名单启动固定模型 worker。模式不构成同 UID 防护、通用用户目录支持或 OS 沙盒，公开 capability 始终 false，产品接收、分发与完整 AC19/AC21 另审。详细状态以最终实现和实测为准，未完成项不能由本文升级为已通过。

## 2026-11-10 Integration 安全复审：同 UID 替换边界仍阻断生产

在本机 macOS 27.0.1 arm64 的临时目录中运行 `python3 docs/ai-001/directory_fd_race_probe.py`，以确定性交错验证：先打开并验证 `ready` 目录 fd，再把其名称移走并换入另一目录，`renameatx_np(outer_fd, "ready", ..., RENAME_EXCL)` 发布了替换对象。该测试的系统调用和两个 inode 的观测见记录。这不是对真实用户文件的攻击，也不是并发概率测试；它表明此系统调用在提交时解析源名称，持有源目录 fd 本身不绑定源名。

本机同一探针另观察 `fclonefileat(ready_fd, ..., destination, 0)` 能从被移名的原目录 fd 创建目标；然而当同 UID 在验证后写入该原目录中的文件，克隆内容就是更改后的内容。`man 2 clonefile` 称克隆预计原子且目标不得存在，同时明确强烈不推荐用它克隆目录；克隆不会把先前校验绑定到不可变字节。这一单机观测不证明其他文件系统或 OS 版本支持、安全、持久性或并发语义。禁止仅用它替换 rename 并声称已解决同 UID 的身份和内容竞态。随机名称、0700、反复 stat、advisory lock 和事后检查均不能阻止同 UID 在两个操作之间改名或改写；事后检查也不能撤销已经短暂公开的错误目录。

可行的下一阶段方案是建立**实际经验证的 OS 强隔离边界**：可信发布者以与不受信写入者不同的安全主体持有并验证 staging/文件，worker 只获得受限输入和一次性写入通道，worker 回收后将已冻结的字节交给该发布者；目标父目录授权和单次无覆盖提交由该主体执行。具体服务身份、权限、接口、模型/音频传递、资源和签名/安装方案需先选型并在真实目标系统上以同 UID 对抗性进程验证。App Sandbox、临时目录、XPC 或 fd 本身不自动构成已证实隔离；不得宣称它们已经解决此问题。目标目录被其他进程在成功发布后再次移动/改写也属于需要单独定义的产品行为。开发 opt-in 继续仅限契约明确的可信命名空间，产品能力维持 false。

## AC19 规范化接口建议（草案，未实现）

- 核心持有单一 job owner，按现有受控进程封装及固定 argv 调用明确配置、版本锁定并按实际构建审查的 `ffprobe`/`ffmpeg`；默认选择和解码的音轨、容器/编码/声道数/采样率都从探测和可证实的完整解码得到，不按扩展名猜测，不通过 shell 拼接参数。多音轨、未知布局、损坏或不支持格式必须明确选择或安全拒绝；不在普通日志泄露绝对路径。
- 最小输入只接受 AC19 的 WAV/FLAC/MP3/M4A、44.1/48 kHz、mono/stereo；需要白名单和失败先行契约测试。单声道以明确的复制规则生成两个相同声道并交 UI 明示，立体声保留左右顺序；禁止默认混入其他声道或擅自变速、加混响。44.1 kHz stereo float32 WAV 是 worker 的内部标准，不得误称输入本来就是该格式。
- 源采样数应由真实解码后的有效采样、压缩格式的 priming/padding 和时间原点共同决定，而非采用容器时长乘采样率的估计；在固定解码器版本下记录适用的 encoder delay/skip/padding，无法证明映射的输入拒绝。规范化目标帧数按 AC19 的 `N=round(decoded_source_frames*44100/source_rate)`；平分取整规则、尾部处理、PTS 偏移与边界信号独立测试须在正式契约冻结，不能用输出相关峰任意平移。两 stem 精确 N 帧、完整解码、有限采样，静音单独验证。
- 规范化输出写入任务所有的私有暂存，永不复用源文件；空间预算增加完整规范化 WAV、容器开销和至少两个最终 stem，并计入四份已 unlink 的 mmap 特征、FFmpeg 的读写及余量。现有可用空间检查不是硬配额；真实受限卷、空间耗尽与取消后资源回收均须单独验收。
- 预检、探测、解码、worker、两 stem 验证与提交共享累计 deadline（队列等待不计）；每个子进程及后代必须有界输出、取消/超时 kill+wait、先回收再清理。经授权路径与内容身份必须贯穿探测到发布；该建议不消除本节所述同 UID 限制。保留旧八函数 ABI 和缺省禁用行为；新增格式范围、错误映射、音轨选择和 UI 语义需先完成 Integration/Core 契约审定、失败测试及独立 QA，不以此草案声称现已支持。

## Integration 补充：本机受保护容器反例

在 macOS 27.0.1 arm64，使用 ad-hoc 签名、app-sandbox entitlement 和系统启动服务实际创建临时发布者容器。同 UID、不同沙盒 App 对容器测试文件写入被拒绝，但另一个从宿主启动的同 UID Python 进程两次成功写入同一文件；其系统授权状态未调查，不推断可推广的绕过方式。可复现源码、二进制哈希和身份详见 隔离探针。不应将 app container 或 XPC 的存在本身视为可抵御任意同 UID 的证明。

对真实 `AtomicDirectory::commit`，另以 [测试插桩](../ai-001/core_commit_race_probe.py)只在独立 Rust 测试二进制及自建临时目录内进行确定性交错：基线通过，插桩后同 UID 子进程在 `renameatx_np` 前替换 `ready`，已发布文件的测试断言读到替换内容并失败；Integration 独立重跑得到相同结论。见 机器证据。这是受控的测试进程插桩反例，不说明未插桩攻击的成功概率，更不是安全通过。

后续待验证的最小替代是独立权限主体持有仅该主体可写的同卷 staging，worker 通过认证的受限通道提交结果，发布主体独立验证内容后原子发布；输入、IPC、服务认证、资源与异常恢复均需安全契约。非该主体的其他本机进程不得能获得对暂存的写权限；目标跨卷、服务无法建立或信任边界无法确认时必须安全拒绝。普通 euid 501 进程不能直接切换到另一 UID（本机 `setuid(1)` 返回 EPERM）；需要明确服务账号、安装授权、签名与生命周期设计，不在此提案中偷偷创建账号或安装特权服务。该方案尚未实现、测试或接收。

即使 staging 由独立主体保护，同 UID 对手若有权改写或移动目标父目录及其祖先，仍可能改变用户看到的路径或在提交后修改结果；持有父目录 fd 只绑定操作的目录对象，不保证其原绝对路径持续指向该对象。应区分提交线性化时的可信数据、目标路径的持续可见性和提交后的外部修改；目标路径安全的实际授权/隔离条件另需设计和验证，不能将安全 staging 直接等同于端到端安全。

## 同 UID 对抗性清理与隔离补充复审

本机 `python3 -B docs/ai-001/cleanup_name_race_probe.py` 使用自行创建的临时文件确定性交错：检查 `vocals.wav` 后，由同 UID 参与者将其移走并放入另一普通文件，接着以持有的目录 fd 调用 `unlinkat`；结果删除的是替换文件，原文件仍在移走的位置。见观测记录。这是系统调用的最小语义探针，**不是对 Core 程序的端到端攻击**；但 Core 当前的 `names(true)` / `verify_identity()` 与后续 `unlinkat(ready_fd, name, 0)` 具有相同的检查与名称删除分离结构，因而静态审查不能排除该交错。持有目录 fd、白名单和删除时不跟随链接不能将先前校验的文件身份绑定到删除对象。对结果目录、`ready` 和外层目录删除也须作同样的名称竞态审查。

发布与清理应一起满足同一威胁边界。直接将现有 `renameatx_np` 换为从 fd 的 `fclonefileat`，虽然在此前本机探针阻止了源目录名替换，却仍可克隆校验后被改写的内容，而且留下的原 staging 仍需安全清理；用此作为完整修复会扩大未验证承诺，因此当前不采用。若资源所有权无法确认，应保留 owner 并 quarantine，而不是根据路径删除未知对象或报清理成功。已存在的受控开发接口仍依赖可信同 UID 命名空间，不提升 capability 或威胁模型。

下一步的可行性实验须把**发布者、工作进程及同 UID 对手**的身份和授权分别明确：目标可能处于外置卷，而 sandbox 容器通常在应用的数据位置；跨卷复制后再在目标卷按名称提交，不能自动继承源卷的隔离或原子性。苹果说明 macOS 14 起，其他应用（包括未启用 App Sandbox 者）访问应用 sandbox 容器可能触发用户授权；一旦用户授予访问或对手具有其他高权限，此假设需单列，不能声称容器天然防御所有同 UID 对手。普通 fork/exec 辅助进程继承宿主 sandbox，单独权限边界须另按 XPC 等机制设计；无论采取何种方案，都需要真实签名/权限模型、同卷及跨卷策略、进程终止后数据冻结、目标授权和对抗测试。见苹果 [App Sandbox 文件访问](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox)及[发现和诊断沙盒违规](https://developer.apple.com/documentation/security/discovering-and-diagnosing-app-sandbox-violations)。这些仅为下一阶段设计约束，不是隔离已实现或验证的证据。

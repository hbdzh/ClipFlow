# ADR-0017：Core 只读导出空间预览

- 日期：2026-11-14
- 范围：CORE-004 JSON 扩展；macOS 定向实现，其他平台未验证

## 问题

AC20 要求用户在提交前看见目标父卷可用空间与输出估算，已知不足时阻止提交。现有队列在接收后才公开计划摘要；直接在 Swift 复制预算公式会使媒体策略出现两个所有者，而先提交再展示会导致未确认就开始执行。

## 决策

增加显式 CORE-004 控制消息 `storage_preview`，在既有 `ms_submit_job` 的 JSON 通道调用，八函数 C ABI、schema_version=0、对象所有权、错误返回及旧消息不变。输入与 `batch_submit.items` 相同的 1..32 个 trim/transcode 子请求，但不接受 submission_id。未启用 CORE-004 的引擎拒绝该操作。

| 行为 | 唯一所有者 |
|---|---|
| 读取实际时间线、输出 budget、同卷累计、已有预留、空间门槛 | Rust media-ffmpeg |
| 调用串行化、与其他接收/AI预留协调、无任务状态变化 | Rust media-orchestrator |
| 保留请求快照与文件授权，展示数值和不保证说明，用户确认后提交 | 原生客户端 |
| 实际输出、失败清理、最终提交 | 既有 Core 执行链 |

预算与实际预检共用 `output_budget`、`reservation_bytes`、`required_storage`：budget=`ceil(duration_us*4100000/1000000)+16MiB`、每项 reservation=`2*budget+64MiB`、同卷 required=`已有同卷预留+本批同卷 reservation 总和+64MiB`。`estimated_output_bytes` 是保守输出预算，不是预测的编码文件大小。原有单项 3GiB 上限保持；同卷项目先累计，不能分别拿同一份可用空间判足够。

预览只读检查源、容器引用、实际时长/区间、目标存在性/父目录身份，并用现有绝对 `/bin/df` 参数数组查询空间。整个请求共用 `timeout_ms`，无新依赖。读取同卷账本时按既有 admission gate 串行化；AI 预留活动或已隔离清理状态时拒绝预览。不建立 plan/target/storage lease，不写 staging/输出，不产生 job ID、提交身份或 worker 唤醒；调用返回后不保留预览。预览不进行编码器、全部媒体适用性或可写性探测，所以只读卷仍可能有足够空间；确认后的原提交会准确拒绝不可写目录。

响应 `ready` 仅表示**当前空间数字可取得且足够**；不是任务被接收或完整预检通过。按卷返回可用、预算、所需空间及原请求下标；卷只用本次数字序号标识，不回显真实路径或设备。空间不足仍保留数值并返回逐项 `OUT_OF_DISK`，其他业务失败用 indexed errors，均不回显工具 stderr/路径。客户端显示“这是空间预算，不是实际成品大小或成功保证；确认后重新预检”，不足/未知时禁用确认；取消不提交。确认后沿用不可变请求进行正常 batch_submit/job_retry，原容量、权限、源身份、目标、实时空间、执行期间耗尽和清理检查保持。

## 验证与回滚

成功场景：同卷两项聚合，保留既有预留，预览后 queue/resources/目录不变。失败场景：空间差 1 byte 则 sufficient=false/OUT_OF_DISK 且保留数字；非法/缺源/目标已存在或 df 失败明确拒绝，无作业。契约另验证空/超32项、未知字段、probe 嵌套等语法拒绝和旧模式拒绝。

本机 GUI 应验确认前无输出、用户取消无接收、已知不足禁用确认、确认后重新预检，以及预检后真实受限卷写满与恢复。Core/ABI/GUI 的证据单独记录，不从文档推定实现通过。可先回滚新客户端确认流程及这条消息，旧 ABI/提交调用仍兼容；不回滚源/输出安全修复。完整发布与其他平台另验。
